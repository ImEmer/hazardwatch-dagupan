# HazardWatch Dagupan System Reference

## 1. Scope and reading notes

This document describes the repository as inspected on 2026-09-17. It covers the application folders, source/configuration files, backend API, frontend API consumers, data models, security controls, and verified security gaps.

`node_modules`, generated build output, package-lock dependency records, and binary image contents are not individually described as handwritten application files. They are identified in the inventory as generated/vendor artifacts. No secrets are reproduced from environment or account files.

## 2. System overview

HazardWatch Dagupan is a React/Vite single-page application backed by an Express 5 API and MongoDB through Mongoose. Citizens submit hazard reports with location and photo evidence. Staff and barangay users review and manage reports; administrators manage users, reports, statistics, contacts, activity, and notifications.

Main runtime flow:

1. `frontend/src/main.jsx` mounts the React application.
2. `frontend/src/App.jsx` provides authentication, theme, reports, routing, layouts, and page-title behavior.
3. `frontend/src/services/api.js` creates the Axios client and injects bearer tokens.
4. The API is mounted by `backend/server.js` under `/api`.
5. `backend/config/db.js` connects to MongoDB.
6. Mongoose models persist users, reports, contacts, activity, notifications, and categories.
7. Cloudinary stores uploaded report images.

Roles are `superadmin`, `admin`, `staff`, `barangay`, and `user`. Barangay users are additionally scoped to their assigned barangay in report, statistics, and activity queries.

## 4. Backend API reference

Base URL: `/api` in local proxy deployments, or the configured `VITE_API_URL`/deployed API origin. Unless marked public, endpoints require `Authorization: Bearer <JWT>`.

### Health and authentication

| Method | Path | Access | Behavior |
|---|---|---|---|
| GET | `/health` | Public | Returns API health and service name. |
| GET | `/auth/check-email?email=` | Public | Normalizes/checks whether an email exists. |
| POST | `/auth/register` | Public | Validates name/email/password, forces unknown roles to `user`, creates an active user, returns a public user projection, and logs registration. |
| POST | `/auth/login` | Public, auth rate limited | Verifies credentials, applies IP/email lockout, handles suspended/banned/deleted accounts, records last login, logs activity, and issues a role-based JWT: one day for admin/superadmin/barangay and seven days for other roles. |
| POST | `/auth/refresh` | Authenticated | Issues a new JWT for the current active user. There is no refresh-token rotation or server-side revocation store. |
| POST | `/auth/logout` | Authenticated | Writes a logout activity record. The bearer token itself is not revoked; the client removes it. |
| GET | `/auth/me` | Authenticated | Returns the authenticated user's public projection. |
| POST | `/auth/change-password` | Authenticated | Checks current password, saves the new bcrypt-hashed password, and logs the change. |
| PUT | `/auth/profile` | Authenticated | Requires name/email, normalizes email, prevents duplicate email, updates profile, and logs the change. |
| DELETE | `/auth/account` | Authenticated | Soft-deletes the current account by setting inactive/deleted state and timestamp, then logs it. |
| POST | `/auth/forgot-password` | Public | Uses a generic response to reduce account enumeration, stores a SHA-256 reset-token hash for 15 minutes, and exposes the raw token only outside production. No email send is implemented in this controller despite email variables/dependency being present. |
| POST | `/auth/reset-password` | Public with token | Hashes submitted token, requires an unexpired stored hash, changes the password, clears reset fields, and logs the reset. |

## 5. External APIs and services used

- MongoDB/Atlas through Mongoose: primary persistence, aggregations, indexes, and geospatial/text queries.
- Cloudinary: report image storage and transformation through `multer-storage-cloudinary`.
- OpenStreetMap raster tiles: map tile source used by MapLibre.
- Nominatim OpenStreetMap reverse-geocoding API: converts map coordinates into an address/barangay in `InteractiveMap.jsx`.
- Deployed HazardWatch API: default frontend base URL when `VITE_API_URL` is absent.
- Local Vite proxy: `/api` and `/uploads` to `http://localhost:5000` during development.
- Vercel: SPA hosting/rewrite configuration in `vercel.json`.
- Nodemailer is listed as a backend dependency and email environment variables exist, but the inspected password-reset implementation does not call an SMTP service.

## 6. Implemented security controls

### Authentication and session controls

- JWT signature verification with `JWT_SECRET` on every protected API request.
- Bearer-token requirement for protected routes.
- Active-user lookup on every request; inactive/deleted users are rejected.
- Role-based API authorization with `allowRoles`, `isAdmin`, and `isStaff`.
- Role-based JWT lifetimes: shorter one-day lifetime for privileged/barangay users and seven days for other roles.
- Client-side token-expiry decoding, five-minute warning, automatic logout at expiry, and 401 session-expiry handling.
- Passwords excluded from normal user queries with Mongoose `select: false`.
- Password hashing with bcryptjs cost factor 12.
- Current-password verification before password changes.
- Short-lived, hashed, one-time reset-token record with generic forgot-password response.
- IP-plus-email in-memory failed-login lockout after three attempts for five minutes.
- Authentication endpoint rate limiting: 100 requests per 15 minutes.
- Public user projection avoids returning password/reset fields from auth responses.

### Authorization and data isolation

- Backend authorization is enforced independently of frontend route guards.
- Admin/superadmin role hierarchy prevents equal/lower privilege violations and self-management.
- Superadmin accounts cannot be modified through the UI; the last active superadmin cannot be suspended, banned, or deleted.
- Barangay report queries are constrained to own or assigned barangay.
- Barangay statistics and activity endpoints reject requests for another barangay.
- Report access requires staff roles except public reduced report listing and authenticated own-report listing.
- Contact management is admin/superadmin only.
- Notification read operations check explicit `userId` ownership.
- Soft deletion is used for users and reports, preserving records rather than immediately removing them.

### Input, file, and response protections

- Helmet sets common HTTP security headers.
- CORS uses an allowlist of known frontend/development origins, credentials, methods, and headers.
- JSON body size is limited to 2 MB.
- Express-validator checks names, email format/normalization, password complexity, categories, custom categories, descriptions, location shape, photo presence, Mongo IDs, pagination, and contact messages.
- Report category values are constrained to a fixed allowlist.
- Custom category is limited to letters/numbers/spaces and 60 characters.
- Search regex input is escaped before database regex creation in report/activity search.
- Pagination limits are bounded for validated routes and activity queries.
- Uploads are limited to three report files, 5 MB per file, and selected image MIME types/extensions; Cloudinary applies a width transformation.
- CSV values are quoted and embedded quotes escaped to reduce CSV structure injection.
- Central error mapping avoids returning raw stack traces in JSON responses, although raw error objects are logged server-side.
- Mongo duplicate, schema-validation, cast, and JWT errors receive controlled status responses.

### Auditability and operational controls

- Registration, login, logout, password changes/resets, profile changes, report submission/updates/status/priority/assignment/comments/deletion, user creation/updates/status/deletion, and account deletion write activity records where implemented.
- Activity logs preserve actor identity, role, barangay, scope, action, message, and target/entity references.
- Database startup checks whether an active superadmin exists.
- `.gitignore` excludes environment files and local test-account documentation.

## 7. Verified security gaps and inconsistencies

These are findings from the inspected code, not claims that a control exists:

1. **Secrets are present in the workspace environment file.** The inspected backend environment file contains real-looking MongoDB, JWT, Cloudinary, and SMTP credentials. Rotate every value, invalidate affected sessions/tokens, remove the file from any Git history or deployment artifact, and use a secret manager/environment injection.
2. **Seed/test credentials are documented in `ACCOUNTS.md`.** The file is ignored, but any copied or deployed version exposes predictable demo passwords. Change or remove all seeded credentials outside isolated development.
3. **The backend README says public report creation is available, but `POST /reports` requires a JWT.** Treat the route implementation as authoritative and update the README/UI expectations if needed.
4. **JWTs are stored in browser storage.** The frontend uses localStorage for citizen sessions and sessionStorage/localStorage fallback for other sessions. Any XSS can read a bearer token. A stronger design uses secure, HttpOnly, SameSite cookies plus CSRF protection, or a short-lived access token held outside persistent storage with a protected refresh mechanism.
5. **Logout and refresh do not revoke or rotate tokens.** A stolen unexpired token remains usable after logout, and refresh issues another JWT without a server-side token family/revocation mechanism.
6. **The login lockout map is process-local.** It resets on restart and is not shared across multiple API instances. Use a distributed rate-limit/lockout store for production.
7. **Password-reset delivery is incomplete.** The controller stores a token and only exposes it outside production; it does not send the reset email. The email dependency/configuration is not used by the inspected reset flow.
8. **The reset-password route lacks the same explicit password validator as registration.** Mongoose enforces only minimum length; it does not enforce the uppercase/lowercase/number/special-character rule used by the client and registration validator.
9. **Server-side Dagupan bounds are not enforced.** The frontend checks the coordinate rectangle, but `validateReport` only checks coordinate shape and the controller accepts the supplied location. A malicious client can submit coordinates outside Dagupan unless server validation is added.
10. **Upload validation trusts the multipart MIME type.** MIME values can be spoofed. Production hardening should inspect file signatures, constrain Cloudinary resource type, and consider malware/content scanning.
11. **Some mutation payloads are insufficiently constrained.** Report update, status, priority, assignment, and comment routes rely partly on Mongoose validation or raw request bodies. Add explicit allowlists/field schemas and length checks at each route.
12. **Bulk report deletion does not validate each ID or write audit records.** It accepts an arbitrary nonempty array and updates matching records. Add per-ID validation, maximum batch size, authorization/scoping checks, and activity logging.
13. **Notifications are polled rather than pushed.** Sidebar counts refresh every 60 seconds; add a push channel only if lower delivery latency becomes a requirement.
14. **Public statistics include all non-deleted reports, including potentially sensitive operational data.** Confirm that totals, categories, and covered areas are intentionally public and do not need active/archived/privacy filtering.
15. **Contact submission has no dedicated abuse/rate limit.** Add throttling, spam controls, and possibly CAPTCHA or moderation if exposed publicly.
16. **The API does not visibly configure HTTPS itself.** TLS may be terminated by Render/Vercel/proxy infrastructure, but production deployment must enforce HTTPS and secure transport at the edge.
17. **Error logging may contain sensitive operational details.** Review production logging destinations and redact credentials, reset tokens, connection strings, and personal data.
18. **No automated test suite was found in the inspected tree.** Add API authorization, barangay isolation, validation, upload, password-reset, lockout, and token-expiry tests before relying on these controls for production assurance.

## 8. Operational recommendations

- Rotate all credentials discovered in the local environment file immediately.
- Add a checked-in `.env.example` containing names only, never values.
- Make server-side report coordinate validation use `utils/dagupanBarangays.js`.
- Add route-level schemas for every mutation and apply the same password policy to reset/change flows.
- Replace process-local lockout with a shared store and add rate limits to contact, reset, and other abuse-prone public endpoints.
- Implement real email delivery for reset tokens and never return reset tokens from a deployed environment.
- Decide on a cookie-based or short-lived-token session architecture and implement token revocation/rotation.
- Add automated security-focused API tests and dependency/audit checks in CI.
- Correct the backend README/API documentation mismatch and document the actual authentication requirements.
